The defensible narrow finding is that, under this Candidate-A model and this

that the predicted state contains the correct future physical/task semantics.

## Protocol and implementation audit

### 1. The recorded split is not 7/1/2 per task

`wm_data.py` first drops every shard whose newly collected `success` field is
false, then computes a 70/10/20 split independently for the remaining count. The
split function therefore exposes 92, not 100, demonstrations: 63 train / 9
validation / 20 test, producing 1,236 / 172 / 367 overlapping windows. The
trainer actually loads only the 63 train and 20 test demos; validation is never
used. Task 2 has 4 / 0 / 2 demos, so validation does not cover every task. The
eight failures are silently filtered even though their indices came from the
earlier replay-valid report.

Required correction: freeze explicit demo IDs in a split manifest, explain or
replay-audit the eight disagreements, and report both demo-level and window-level
counts. Do not claim a fixed per-task 7/1/2 split for these runs.

### 2. The current `test` split has been consumed as development data

`train_a.py` never loads validation. The same `test` demos were used to compare
input arms, diagnose rank, derive a replacement rank threshold, choose variance
regularization, and issue the final decision. These results remain useful, but
the split is now **dev**, not untouched test evidence.

Required correction: use a repaired validation/dev split for all input, objective,
and architecture selection. Draw a new untouched audit split from demos that have
not entered these decisions, save its IDs/hash, and keep it closed until the full
Candidate-A/B protocol and configuration are frozen. The audit split is for one
frozen verification, not another round of selection.

### 3. Current F1 / R² are readouts of encoded present state, not predicted future

Predicate, progress, and proprio heads are trained and evaluated on teacher-forced
encoder carries `Z_t`. They are not evaluated on transition rollouts
`Zhat_{t+k}`. The reported predicate F1 ≈ 0.99 and progress R² ≈ 0.94 therefore do
not show that the model predicts future predicates or task progress. In addition,
the current progress target is normalized recorded-demo step index, i.e. phase,
not semantic predicate progress or remaining time.

Required correction: apply the shared heads to every `Zhat_{t+k}` and score future
predicate bits, proprio/object state, semantic progress, and phase separately for
`k=1..4`. Report per-task/per-demo metrics and trivial task/phase priors.

### 4. Action sensitivity has an action-history shortcut

The target encoder for `Z_{t+1}` receives `a_prev = a_t`, while the transition
also receives `a_t`. A shuffled action can therefore hurt because the transition
cannot reproduce action-history content in the learned target, even without
modeling the physical consequence of the action. The current shuffle is also
cross-batch, mixing task and phase, so it is a coarse OOD intervention.

Required correction: add matched within-task/phase action shuffles, a separately
trained no-action model, and future physical readouts from `Zhat`. Either remove
previous-action content from the prediction target or explicitly separate it from
the world-state portion whose dynamics are being evaluated.

### 5. The task intervention checks difference, not correctness

Oracle task embeddings enter the encoder through FiLM and enter Transition
directly. Nonzero carry/head change after shuffling task ID is therefore
architecturally easy to produce and is insufficient evidence by itself. The current
`tau_dpred/tau_dprog` values are computed from teacher-forced encoded carries, not
predicted futures; they do not establish that the state changes toward the correct
alternative task semantics. For real-LL and fused arms, the stored
prompt-conditioned tokens also remain tied to the original task while only the task
ID is swapped.

Required correction: add task-only and no-task baselines, same-physical-history
t0↔t1 interventions with consistent input construction, future-semantic scoring,
and same-task paraphrase consistency. A latent difference alone is not the project
criterion.

### 6. The rank conclusion does not follow the registered branch literally

The registered ablation rule defines reference `(a)` as EMA target-carry rank and
declares a fix at `>= 0.5 × (a)`. With EMA rank 16.7, that bar is 8.35; the
anchor×0.5 run at rank 16.1 already satisfies it while retaining criteria a/b/c.
Thus the registered condition "if neither fixes" was not reached. Replacing the
bar with `0.5 × raw-token rank = 18.3` is a documented post-hoc rule change, not
an execution of the literal pre-registration.

The raw reference is also only descriptive: mean-pooling 128 tokens followed by a
random projection is not naturally commensurate with a flattened learned 4×384
carry, and the EMA reference comes from the model being audited. Effective rank
should remain a collapse diagnostic, not a hard certification threshold yet.

### 7. Variance regularization is a trade-off, not zero-cost

Variance regularization raises rank to 18.9 / 19.3, but relative to the matching
base runs it worsens k-step cosine prediction error by roughly 40–70%. Copy margin
falls from 0.75→0.69 and 0.79→0.69; seed-1 action sensitivity falls
1.10→0.95. The model still clears the provisional functional thresholds, but the
artifact does not support "zero cost."

Required correction: report EMA/no-var and EMA+var as a prediction/rank Pareto
comparison on the corrected dev protocol. Keep variance weight open until the
downstream future-readout metrics and untouched audit agree.

### 8. Sequential collection misses the terminal post-block state

Each record is captured before its action block. If success occurs inside the last
block, no successor observation/predicate is appended. This removes exactly the
terminal transition needed for predicate completion and value learning; task 5's
stored predicate bits are all false despite successful shards.

Required correction: append the observation, predicate bits, proprio/object state,
success, and terminal flag after every executed block, including the final partial
or successful block according to an explicitly documented policy.

### 9. Run artifacts are not yet self-describing

The result JSONs record arm, seed, epochs, parameter count, curves, and aggregate
diagnostics, but not `anchor_scale`, `var_reg`, learning rate, batch size, objective
weights, split demo IDs, git/environment fingerprint, or per-demo metrics. The
interpretation of `ablA/ablB` therefore depends on the dated prose and run naming,
not the artifact alone.

Required correction: serialize the complete resolved config, split-manifest hash,
code/environment fingerprint, and per-demo/per-task metrics into every subsequent
report.
